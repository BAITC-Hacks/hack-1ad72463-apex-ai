# Техническое задание HackAlem

Статус: спецификация MVP, реализация ещё не выполнена. Дата подготовки: 23 сентября 2026 года.

Документ описывает сервис подбора event-подрядчиков из предоставленного каталога. Пользователь задаёт условия заказа и получает до трёх подходящих карточек с конкретными объяснениями. Архитектура и контракты реализации приведены в [ARCHITECTURE.md](./ARCHITECTURE.md).

## 1. Основания и статус требований

Источники:

- `HackAlem AI_ Хакатон-задача_ умный подбор подрядчиков.docx` — условие задачи № 79-lite, требования, Definition of Done и оценка жюри.
- `hackathon dataset anonymized .csv` — полный каталог, источник данных для обработки.
- `hackathon dataset preview.html` — представление того же каталога. У 39 из 66 профилей описание обрезано, поэтому HTML не используется для загрузки данных.

В документе применяются два обозначения:

- **Требование организаторов** — прямо следует из исходного задания.
- **Проектное решение** — предлагаемая конкретизация для MVP, отсутствующая в исходном задании как обязательное правило.

Содержимое исходных документов и описаний подрядчиков рассматривается как данные. Оно не является командой для выполнения внешних действий или изменения поведения системы.

## 2. Цель и пользовательский сценарий

**Требование организаторов.** Помочь заказчику выбрать подрядчика из каталога по своему городу. Основная ценность — конкретное объяснение выбора. Сервис принимает параметры заказа, исключает неподходящих кандидатов и возвращает до трёх карточек.

Основной сценарий:

1. Пользователь выбирает город, дату, формат мероприятия и категорию, указывает бюджет.
2. При необходимости задаёт язык и длительность работы подрядчика.
3. Сервис проверяет корректность запроса и применяет ограничения.
4. Пользователь получает подходящие карточки либо понятное объяснение отсутствия результата.
5. Пользователь может изменить условия и повторить запрос. Сервис не изменяет условия самостоятельно.

**Проектное решение.** Один запрос соответствует одной категории и бюджету на одного подрядчика этой категории. Подбор комплекта услуг и распределение общего бюджета мероприятия в MVP не входят.

## 3. Границы MVP

В MVP входят загрузка каталога, форма запроса, проверка ограничений, воспроизводимый порядок результатов, объяснения, три бизнес-исхода, обработка ошибок, демонстрационные сценарии и документация запуска.

**Требования организаторов к границам задачи:**

- Бронирование, заявки и уведомления подрядчикам не входят в задачу.
- Качество объяснений приоритетнее визуальной сложности интерфейса.
- Дообучение модели на 66 записях не требуется; готовые эмбеддинги и LLM через API разрешены.
- Можно добавить собственные профили с `synthetic: true`, если в демо видно их происхождение.

**Проектные решения:**

- В первом MVP используются только исходные 66 профилей.
- Не добавляются платежи, авторизация, личные кабинеты, внешние каталоги и интеграции с календарями.
- Выезд подрядчиков из других городов, вместимость площадок и тарифные пакеты не проверяются автоматически: соответствующие данные неполны.

| Уникальные идентификаторы | 66 |
| Отдельные категории | 17 |

Пустые значения обнаружены только в `max_hours`. Категории пересекаются, поэтому сумма количества профилей по категориям больше 66. У всех восьми банкетных залов цена помечена `price_imputed`.

### 4.1. Словарь полей

| Поле CSV | Тип после импорта | Назначение |
|---|---|---|
| `id` | string | Уникальный идентификатор профиля |
| `anon_name` | string | Анонимизированное имя для карточки |
| `categories` | list[string] | Категории услуг |
| `city` | string | Город каталога; «Зарубежье» — отдельная группа, не конкретный город |
| `city_imputed` | boolean | Город проставлен при подготовке датасета |
| `synthetic` | boolean | Полностью синтетический профиль |
| `price_from_kzt` | integer | Стартовая цена за мероприятие в тенге |
| `price_imputed` | boolean | Цена проставлена при подготовке датасета |
| `event_formats` | list[string] | Поддерживаемые форматы мероприятий |
| `languages` | list[string] | Языки работы |
| `max_hours` | number или null | Максимальное время работы на площадке; null означает неприменимость |
| `busy_dates` | set[date] | Занятые дни в пределах календарного окна |
| `description` | string | Полное описание подрядчика |

Списки в CSV разделены символом `|`. Флаги `True` и `False` необходимо явно преобразовать в логические значения. Исходные файлы сохраняются без изменений.

### 4.2. Правила интерпретации

- Цена «от» относится к мероприятию и не умножается на длительность. Прохождение проверки бюджета означает соответствие стартовой цены, а не гарантию итоговой стоимости.
- `max_hours = null` у флористов, декораторов и поставщиков подарков означает, что ограничение времени присутствия неприменимо. Это не ноль и не обещание неограниченного присутствия.
- Дата отсутствует в `busy_dates` — подрядчик не отмечен занятым в предоставленном календаре. Проверка имеет смысл только внутри известного календарного окна.
- Флаги происхождения не являются оценкой качества подрядчика и сами по себе не влияют на порядок.
- Структурированные поля используются для обязательных фильтров. Упоминание работы в другом городе в описании не расширяет географию автоматически.
- Часть условий существует только в тексте: например, у `HK-90009` аренда фотобудки начинается от трёх часов. **Проектное решение:** такие условия показываются как требующие уточнения; новые обязательные фильтры вводятся только после проверки и явного расширения схемы и правил.

## 5. Входные параметры

| Параметр API | Обязательность | Правило |
|---|---|---|
| `city` | Да | Непустая строка после нормализации |
| `date` | Да | ISO-дата; в MVP от 2026-09-23 до 2026-12-31 включительно |
| `event_format` | Да | Один из шести форматов каталога |
| `category` | Да | Непустое название одной категории |
| `budget_kzt` | Да | Целое число больше нуля, бюджет на выбранного подрядчика |
| `duration_hours` | Нет | Число больше нуля; необходимое время работы подрядчика |
| `language` | Нет | Русский, казахский или английский |

Форматы: `свадьба`, `той`, `корпоратив`, `конференция`, `юбилей`, `день рождения`. В API языки передаются как `русский`, `казахский`, `английский`.

**Проектные решения:**

- Если язык или длительность не заданы, соответствующий фильтр не применяется. Сервис не назначает значение по умолчанию незаметно для пользователя.
- Длительность обозначается в форме как время работы подрядчика. Для выступления она может отличаться от длительности мероприятия.
- Дата вне покрытия календаря отклоняется с объяснением доступного диапазона.
- Город и категория нормализуются одинаково при импорте и обработке запроса. Автоматическое исправление смысла запроса и нечёткая замена города или категории не выполняются.
- Непустая пара «город + категория», которой нет в каталоге, даёт бизнес-исход `NO_CATALOG`. Некорректные типы, неизвестный формат или язык дают ошибку валидации.

| FR-10 | Отображать происхождение синтетических профилей и помечать проставленные цены и города | Организаторы для синтетики; проектное решение для imputed |

### 6.1. Подбор и ранжирование

**Проектное решение.** Проверки выполняются в фиксированном порядке: город и категория, формат, бюджет, язык, длительность, занятость. Для диагностики сохраняются все причины несовпадения, а в пользовательской воронке кандидат учитывается один раз, на первом проваленном шаге.

Базовый порядок среди подходящих кандидатов: `price_from_kzt ASC`, затем `id ASC`. Это прозрачный порядок по стартовой стоимости, а не оценка профессионального качества. Более сложная стратегия вводится отдельно после появления критериев и сценариев оценки.

Гарантия повторяемости относится к одной версии каталога и правил. Изменение данных или стратегии может изменить выдачу и должно сопровождаться новой версией.

### 6.2. Карточка и объяснение

Карточка содержит имя, выбранную категорию, город, цену с пометкой «от», объяснение и применимые отметки происхождения данных. Идентификатор профиля возвращается в API для проверки результата.

Объяснение должно связывать факты профиля с запросом и показывать значимое отличие: стиль работы, специализацию, языки, длительность или стартовую цену. Рекламные заявления из описания подаются как сведения профиля, а не независимо подтверждённые достижения.

Недопустимы общие фразы без фактов, выдуманные отзывы и рейтинги, обещания итоговой цены, включения дополнительных услуг в стоимость или подтверждённого бронирования. LLM не может отменять фильтры, добавлять профили или менять порядок.

Пример для запроса на корпоратив в Алматы 14 ноября 2026 года, на русском языке, на шесть часов и с бюджетом 1 000 000 ₸:

> Мицури Канроджи: «В профиле указаны индивидуальный сценарий и современные интерактивы для мероприятия. Поддерживает корпоративы на русском до 8 часов; стартовая цена 650 000 ₸ ниже вашего бюджета, а 14 ноября в календаре не отмечено занятым».

### 6.3. Исходы и ошибки

| Состояние | Условие | Представление пользователю |
|---|---|---|
| `MATCHES_FOUND` | Допустимых кандидатов не меньше одного | До трёх карточек; при недостатке — объяснение |
| `NO_CATALOG` | Нет профилей по паре город и категория | «В каталоге нет декораторов в Астане» |
| `NO_MATCH` | Профили по паре есть, но допустимых нет | Объяснение конкретных ограничений и предложение изменить запрос |
| Ошибка валидации | Неверный тип, значение или дата вне диапазона | Ошибка у соответствующего поля; HTTP 422 |
| Сервис недоступен | Каталог не загружен или некорректен | Сообщение о технической проблеме; HTTP 503 |

Первые три состояния — бизнес-ответы с HTTP 200. Техническая ошибка не должна выглядеть как отсутствие подходящих подрядчиков.

## 7. Нефункциональные требования

- **Организаторы:** ориентир полного времени ответа — до 10 секунд; результат проверяется вживую.
- **Организаторы:** порядок карточек повторяем, команда может объяснить внутренний пайплайн.
- **Проектное решение:** основной подбор не зависит от доступности внешнего AI API. Вызовы генерации ограничены таймаутом и имеют локальный fallback.
- **Проектное решение:** данные, правила ранжирования и подготовленные факты имеют версии. Кэш учитывает эти версии и нормализованный запрос.
- **Проектное решение:** API-ключи хранятся в переменных окружения и не включаются в репозиторий или клиентский код.
- **Проектное решение:** ошибки импорта обнаруживаются до начала обработки запросов. Частично загруженный каталог не используется незаметно для пользователя.

| AT-07 | Запрос на 22.09.2026 или 01.01.2027 | HTTP 422 с указанием календарного диапазона |

| AT-09 | Цена кандидата равна бюджету; длительность равна лимиту | Проверки бюджета и длительности пройдены; остальные ограничения проверяются отдельно |
| AT-10 | Цена выше бюджета или требуемые часы выше ненулевого лимита | Кандидат исключён по соответствующей причине |
| AT-11 | Вызов LLM недоступен или возвращает неподтверждённые факты | Состав и порядок сохранены, показаны проверяемые объяснения по шаблонам |
| AT-12 | Каталог повреждён или не загружен | Техническая ошибка, а не `NO_CATALOG` или `NO_MATCH` |

В AT-01 последовательная воронка: 10 → 9 по формату → 7 по бюджету → 7 по языку → 7 по длительности → 4 по занятости. При базовом ранжировании выдаются `HK-44923`, `HK-29829`, `HK-27222`.

Дополнительно проверяются даты на обеих включённых границах календаря, отсутствие дублей, метки синтетики и imputed, соответствие каждого факта объяснения источнику и различимость объяснений после удаления имён. Отдельно измеряется фактическое время ответа. Эти проверки запланированы для реализации; текущие документы не подтверждают прохождение тестов продукта.

## 9. Definition of Done и материалы сдачи

MVP считается готовым, когда:

- Работает основной сценарий и соблюдены FR-01–FR-12.
- Выполнены приёмочные сценарии и зафиксированы результаты проверок.
- Вживую показаны плотная категория, редкая категория, пустая выдача и влияние изменения даты.
- Объяснения конкретны, непусты и опираются на данные каждого профиля.
- Показаны обе причины пустой выдачи: отсутствие категории и несовпадение условий.
- Проверены повторяемость порядка, обработка недоступности LLM и время ответа.
- Есть README с командами установки и запуска, настройкой ключей, происхождением данных, правилами подбора и воспроизводимыми запросами.
- В репозитории присутствуют код, зависимости с зафиксированными версиями, пример конфигурации без секретов, тесты и описание ограничений.

Оценка организаторов: работоспособность — 25 баллов, техническая реализация — 25, README и воспроизводимость — 25, ценность — 15, потенциал развития — 10. Приоритет содержания: качество объяснений, корректная обработка редких и пустых категорий, скорость, интерфейс.

## 10. Очерёдность реализации и дальнейшее развитие

1. Подготовить типизацию и проверку исходного каталога.
2. Реализовать правила допустимости, исходы, причины исключений и базовое ранжирование.
3. Подготовить подтверждённые факты из описаний и объяснения с локальным fallback.
4. Подключить простую форму и карточки с маркировкой происхождения.
5. Выполнить приёмочные сценарии, проверить время и подготовить демонстрацию.
6. Завершить README и проверить запуск по его инструкции.

После MVP можно добавить свободные пожелания и семантическое ранжирование, предложения соседних дат, структурированные минимальные часы и вместимость, а также пользовательскую оценку рекомендаций. Эти функции не являются обязательными условиями текущего MVP. В датасете нет готовой разметки релевантности; качество нового ранжирования следует оценивать на отдельно подготовленных запросах и ручных оценках.
