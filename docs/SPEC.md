# Apex Match — frontend-спецификация MVP

## 1. Статус и источники истины

Мы реализуем только веб-интерфейс Apex Match. Backend, загрузка CSV, фильтрация, ранжирование и AI-факты находятся в зоне другой команды. Пользователь подтвердил, что backend будет переписан на Go. Упоминание Python в `ARCHITECTURE.md` теперь устаревшая реализационная деталь; frontend не зависит от языка backend.

При противоречиях приоритет имеют:

1. [`TECH_SPEC.md`](../TECH_SPEC.md) — требования, бизнес-статусы и приёмочные сценарии;
2. [`ARCHITECTURE.md`](../ARCHITECTURE.md) — backend-пайплайн и предложенный HTTP-контракт;
3. этот документ — поведение и архитектура frontend.

Проверенный CSV содержит 66 профилей и ожидаемые 13 полей; его SHA-256 — `6a724b6b7dfb5973343e68ba18dadb60fc807d87e3d78f03ee86fb26cb089f7d`. CSV не добавляется в frontend-бандл и не коммитится без отдельного решения.

## 2. Цель и пользователь

Заказчик мероприятия должен быстро задать условия, увидеть до трёх подходящих карточек или понятную причину пустой выдачи. Frontend не дополняет каталог, не пересортировывает ответ и не ослабляет запрос незаметно.

## 3. Требования организаторов P0

| ID | Frontend-поведение |
|---|---|
| REQ-001 | Форма требует город, дату, тип мероприятия, категорию и бюджет KZT; язык и длительность опциональны. |
| REQ-002 | Дата — date-only `YYYY-MM-DD`, без UTC-сдвига; UI ограничивает 2026-09-23…2026-12-31, но всё равно показывает backend-ошибку даты. |
| REQ-003 | `MATCHES_FOUND` показывает 1–3 карточки в порядке API. |
| REQ-004 | Карточка показывает имя, выбранную категорию, город, цену с меткой «от», 1–2 предложения `explanation` и флаги происхождения. |
| REQ-005 | `synthetic`, `city_imputed`, `price_imputed` не скрываются и не показываются как оценка качества. |
| REQ-006 | Если допустимых меньше трёх, UI показывает фактическое число и backend-`message`/диагностику; пустые карточки не дорисовываются. |
| REQ-007 | `NO_CATALOG` и `NO_MATCH` — два разных пустых состояния; `422` и `503` — ошибки, а не пустые результаты. |
| REQ-008 | Повторный submit того же запроса не меняет порядок, полученный от API; React key — `id`, а не индекс. |
| REQ-009 | Loading-состояние понятно до 10 секунд; повторный submit не создаёт дубль. |
| REQ-010 | Демо покрывает плотную, редкую и пустую выдачу, а также смену даты. |
| REQ-011 | Ни frontend, ни mock не заявляют реальную доступность, итоговую цену или качество подрядчика. |

## 4. Frontend-архитектура

**Выбор:** React + TypeScript + Vite. React и Vue не используются одновременно. React выбран как минимальное отклонение от ранее предложенного TypeScript-стека; Vite достаточен для SPA с отдельным Go backend. Ради скорости не добавляются SSR, Redux, маршрутизатор для одного экрана, отдельный design system и тяжёлый UI-kit. Допустимы только runtime-валидатор схемы и минимальный набор тестовых зависимостей.

```text
frontend/
  src/
    app/                 # composition, providers, styles
    pages/search/        # SearchPage and page state
    features/search/     # form, submit use case, result states
    entities/provider/   # card and display model
    shared/api/          # DTO, gateway, HTTP and mock adapters
    shared/ui/           # Button, Field, Alert, Spinner
  tests/
```

Поток данных:

```text
SearchForm -> SearchRequest DTO -> RecommendationGateway
  -> MockRecommendationGateway (now) OR HttpRecommendationGateway (later)
  -> runtime response validation -> SearchViewState
  -> ResultCards | NoCatalog | NoMatch | FieldErrors | ServiceError
```

### Границы слоёв

- Компоненты не вызывают `fetch` напрямую.
- `RecommendationGateway` возвращает типизированный result и скрывает mock/HTTP.
- DTO зеркалят `ARCHITECTURE.md`; view model может только форматировать, но не менять смысл.
- Ответ валидируется на runtime-границе. Несовместимый ответ показывает техническую ошибку, а не частичные карточки.
- Выбор адаптера — одна environment-настройка; mock не попадает в production молча.

## 5. Форма и состояния

Поля валидируются на blur и submit. Клиентская валидация улучшает UX, но не заменяет backend-валидацию. `duration_hours` и `language` отправляются как `null` или опускаются в точном соответствии с финальным backend-контрактом.

Машина состояний страницы:

```text
idle -> validating -> loading
loading -> success | no_catalog | no_match | validation_error | service_error
any terminal state -> validating on explicit resubmit
```

- При `loading` submit отключён, поля остаются видимыми.
- Новый запрос отменяет предыдущий через `AbortController`; запоздалый ответ не перезатирает актуальный.
- `422` маппится на поля; неизвестная ошибка остаётся общей.
- `503`, network error, timeout и invalid response дают `service_error` с кнопкой повтора.
- На экране никогда не смешиваются новые карточки и старая ошибка.

## 6. Mock до готовности API

Mock — обычная frontend-зависимость, а не временный `if` в компоненте. Он возвращает пять явных сценариев: `MATCHES_FOUND` с 1, 2 и 3 карточками, `NO_CATALOG`, `NO_MATCH`, а также ошибки `422` и `503` по тестовой настройке.

Все mock-записи:

- имеют `id` с префиксом `FIX-` и явную метку `synthetic: true`;
- не выдаются за реальные записи CSV;
- хранятся в `shared/api/mock`, а не в JSX;
- проходят ту же runtime-схему, что HTTP-ответ;
- не реализуют самостоятельную бизнес-логику подбора.

Переключение на backend меняет composition root и base URL, но не компоненты.

## 7. Объяснения, диагностика и безопасность

- `explanation` показывается как текст, не HTML; frontend не дописывает факты из `description`.
- `conditions_to_confirm` показываются отдельно как требующие уточнения, а не как проверенные факты.
- `message`, тексты ошибок и все строки API недоверенные: React экранирует их, `dangerouslySetInnerHTML` запрещён.
- Frontend не содержит AI/API-ключи и не вызывает LLM напряму.
- Диагностика нужна для объяснения пустых состояний, но не показывает служебные версии или пути.

## 8. P1 — не блокирует P0

1. **«Что изменить?»** UI показывает только альтернативы, вычисленные backend реальным повторным поиском. Frontend не ищет даты и не вычисляет минимальный бюджет. Альтернатива применяется только по клику, меняет ровно одно поле и затем отправляет новый запрос.
2. **AI-интерпретация.** Frontend может показать текстовое поле и предложенные backend значения в форме. Поля не заменяются без подтверждения; недоступность AI не ломает ручную форму.

## 9. Вне объёма frontend

Загрузка и аудит CSV, фильтры, ранжирование, счётчики, объяснения, AI-вызовы, бронирование, авторизация, платежи, мобильное Flutter-приложение и production-аналитика не входят в этот этап.

## 10. Оставшиеся неизвестные

- Фактические endpoint, base URL, CORS-политика и метод получения опций формы ещё не подтверждены.
- `ARCHITECTURE.md` предлагает `POST /api/recommendations`; frontend закрепляет это только как текущий ожидаемый контракт. Изменение URL должно затронуть только HTTP-адаптер.
- Источник опций формы не задан. До появления meta endpoint frontend держит версионный fallback-справочник только для полей, явно помечая его как временный. Он не содержит профили и не делает подбор.
- До готовности backend нельзя заявлять, что интеграция или сквозной поиск проверены.
