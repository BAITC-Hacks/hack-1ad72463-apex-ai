# Apex Match — frontend-план на 240 минут

## 1. Допущение и цель

240 минут — плановый бюджет от начала этапа, включая документацию. Это не обещание готовности. Приоритет — быстро получить демонстрируемый frontend с mock-адаптером, затем заменить адаптер на Go API без переделки UI. Последние 30 минут зарезервированы под проверки и сдачу.

P1 (альтернативы и AI-ввод) не начинается, пока P0 не работает на mock и не подтверждён HTTP-контракт. При любом отставании P1 удаляется целиком.

## 2. Команда и три ветки

| Участник | Ветка | Роль | Зона файлов |
|---|---|---|---|
| Санжар | `feat/frontend-contract-sanjar` | A, интегратор: scaffold, типы, runtime-схемы, gateway, mock, затем HTTP-стык с Go backend | `frontend/package*`, `frontend/vite.config.*`, `frontend/tsconfig*`, `frontend/src/app/bootstrap*`, `frontend/src/shared/api/**`, `frontend/src/shared/config/**` |
| Виктор | `feat/frontend-ui-viktor` | B, frontend: форма, карточки, состояния, адаптивность | `frontend/src/pages/**`, `frontend/src/features/**`, `frontend/src/entities/**`, `frontend/src/shared/ui/**`, `frontend/src/app/styles/**` |
| Алина | `test/frontend-qa-alina` | C, облегчённый QA: приёмочные сценарии, ручное демо, простые component tests | `frontend/tests/acceptance/**`, `frontend/tests/components/**`, без изменения production-кода |

Почему так: Санжару отдаётся стык с Go API и общие типы; Виктор ведёт весь UI без конфликтов с API-файлами; у Алины нет Codex-подписки, поэтому её зона меньше, не содержит критических общих файлов и не блокирует P0.

### Порядок старта веток

1. После публикации `docs/contractor-plan` Санжар создаёт `feat/frontend-contract-sanjar` от SHA этого плана.
2. К T+45 Санжар пушит scaffold-коммит: Vite/React/TS, точки входа, пустые каталоги и согласованные зависимости. Бизнес-заглушек в нём нет.
3. Виктор и Алина создают свои ветки **от SHA scaffold-коммита**, а не от старого `main`.
4. PR Виктора и Алины нацелены на `feat/frontend-contract-sanjar`. Санжар собирает интеграционную ветку; только она затем идёт в `main`.

Это даёт одну короткую последовательную зависимость в 15 минут, но убирает три параллельных scaffold и конфликты lock-файла.

## 3. План по минутам

| Окно | Владелец | Работа и файлы | Зависимость | Критерий приёмки | Не менять |
|---|---|---|---|---|---|
| T+0…30 | Санжар | Этап документации и контрактов | Новые root-документы учтены | Контракт не противоречит `TECH_SPEC.md` | Исходные данные и root-документы другой команды |
| T+30…45 | Санжар | React/Vite/TS scaffold, test runner, lint/typecheck scripts | Одна ветка | Чистый пустой экран собирается; SHA отправлен | Не добавлять Next, Redux, UI-kit |
| T+45…90 | Санжар | DTO, runtime-схема, gateway, mock-сценарии | Утверждённый API-черновик | Mock возвращает 1/2/3, `NO_CATALOG`, `NO_MATCH`, 422, 503; schema ловит поломку | Не реализовывать backend-поиск |
| T+45…105 | Виктор | Форма, layout, карточки, badges, loading/пустые/ошибочные состояния | Scaffold и gateway interface | Все состояния показываются без hard-coded API в JSX | Не менять `shared/api`, package/lock |
| T+45…80 | Алина | Перенос сценариев из `ACCEPTANCE.md` в короткий checklist; 3–4 простых component tests | Scaffold и готовые компоненты по мере появления | Проверены форма, два пустых состояния, ошибка, badges | Не менять production-код и dependencies |
| T+90…120 | Санжар + Виктор | Первый сквозной frontend-поток на mock; merge UI в integration branch | Оба блока готовы | **Веха T+120:** форма → gateway → 3 карточки/пустое состояние | Не выдавать mock за Go API |
| T+120…150 | Виктор | Responsive 360px/desktop, focus, labels, визуальная иерархия | Сквозной mock-поток | Keyboard-проход и mobile layout без overflow | Не делать редизайн |
| T+120…165 | Санжар | HTTP-адаптер к Go API, если URL/schema/CORS подтверждены | Готовый Go endpoint | Переключается одна config; contract test проходит | Не менять UI под ответ вручную |
| T+150…180 | Алина | Ручной прогон P0, фиксация точных дефектов | Integration branch | По каждому дефекту есть шаг, ожидание, факт | Не исправлять чужую зону |
| T+165…180 | Санжар + Виктор | P0-дефекты, contract drift, loading race | QA-результаты | Нет known P0 blocker | Новые функции запрещены после T+180 |
| T+180…210 | Все | Демо, типы, тесты, сборка; Go API или честный mock-режим | Feature freeze | Выбор режима видим; README не лжёт о backend | Только fixes |
| T+210…240 | Санжар (координация) | **Резерв:** clean install/build/test, Git status, демо-прогон, сдача | Все изменения слиты | Воспроизводимый запуск и статус зафиксированы | Никаких features |

## 4. Контрольные точки

- **T+45:** scaffold freeze; только Санжар меняет dependencies и общие config.
- **T+90:** DTO/mock freeze; изменение только при доказанном backend contract drift.
- **T+120:** первый настоящий frontend E2E на mock. Если его нет, все силы идут на P0.
- **T+150:** запрет на P1, если Go API не подключён или P0 QA не начат.
- **T+180:** feature freeze в любом случае.
- **T+210:** release freeze; допустим только rollback регрессии или исправление сдачи.

## 5. Сокращённый план на 180 минут

P1 удаляется первым. Затем сокращаются полировка и число автотестов, но не основные состояния.

| Окно | Результат |
|---|---|
| 0…25 | Документы и контракт |
| 25…40 | Scaffold от Санжара; ветки от его SHA |
| 40…85 | Параллельно: gateway/mock, UI, QA checklist |
| 85…110 | Первый frontend E2E на mock |
| 110…135 | P0-дефекты; HTTP-адаптер только если API готов |
| 135…150 | Feature freeze, короткое QA и демо |
| 150…180 | Неприкосновенный резерв на проверку и сдачу |

## 6. Риски

| Риск | Влияние | Реакция |
|---|---|---|
| Go API не готов или меняет схему | Нет сквозного поиска | Показывать mock-режим честно; сменить только adapter после contract tests |
| CORS/base URL не согласованы | Browser-запрос блокируется | Согласовать до T+90; не обходить небезопасным proxy |
| Слишком ранний UI polish | Пустые/ошибочные состояния не готовы | Сначала все состояния, затем адаптивность, затем косметика |
| Ветки трогают общие файлы | Merge-конфликт в конце | Соблюдать таблицу владения; общие типы/deps меняет только Санжар |
| Алине дают критический code path | Отсутствие Codex создаёт блокер | Алина не владеет production-кодом; её незавершённая задача не блокирует демо |

## 7. Что не делать в MVP

Не добавлять SSR, Redux, React Router для одной страницы, Storybook, собственный design system, клиентскую БД, сложные анимации, i18n, тёмную тему, offline-режим или прямой вызов LLM. Эти функции не улучшают критический демо-поток за доступное время.
