# Apex Match — frontend-приёмка

Это план будущих проверок, а не отчёт о прохождении: frontend ещё не реализован. Бизнес-логика проверяется на Go backend; frontend проверяет свой контракт, рендеринг и состояния.

## 1. Явно синтетические frontend-фикстуры

Все unit/component tests используют `FIX-*`, `synthetic: true` и не имитируют реальные профили. Нужны фикстуры:

- `MATCHES_FOUND` с 1, 2 и 3 карточками;
- `MATCHES_FOUND` с `eligible_count=4`, но тремя `results`;
- `NO_CATALOG` и `NO_MATCH`;
- `422 VALIDATION_ERROR`, `503 CATALOG_UNAVAILABLE`, network error, timeout;
- невалидный JSON/нарушенный инвариант ответа;
- карточки с каждым provenance-флагом, `max_hours=null`, `conditions_to_confirm` и опасным текстом вроде `<img onerror=...>`.

## 2. Автоматические frontend-проверки

| ID | Требование | Проверка | Ожидание |
|---|---|---|---|
| FE-001 | REQ-001 | Submit с пустым обязательным полем | Gateway не вызван; ошибка связана с полем и доступна скринридеру. |
| FE-002 | Дата | Ввести невалидную дату, 2026-09-22, 2027-01-01 и обе границы | Вне окна — field error; 2026-09-23 и 2026-12-31 разрешены; день не сдвигается timezone. |
| FE-003 | Числа | Бюджет 0, отрицательный, дробный; длительность 0/NaN | Неверные значения не уходят в gateway; бюджет целый `>0`, длительность конечная `>0`. |
| FE-004 | Сериализация | Заполнить все поля, затем убрать язык/часы | DTO имеет точные `city`, `date`, `event_format`, `category`, `budget_kzt`; optionals опущены или `null` по контракту. |
| FE-005 | 1, 2, 3, 4+ | Параметризованно подать фикстуры `returned_count=1/2/3`, затем `eligible_count=4`, `results=3` | Ровно столько карточек; при 1/2 видна причина; при 4+ нет четвёртой карточки. |
| FE-006 | REQ-007 | Подать `NO_CATALOG`, затем `NO_MATCH` | Разные заголовки/действия; `NO_CATALOG` не обвиняет бюджет/дату, `NO_MATCH` показывает диагностику. |
| FE-007 | 422/503 | Подать оба ErrorResponse | 422 привязан к полю; 503 — общая техническая ошибка с retry, не `NO_MATCH`. |
| FE-008 | Loading/race | Задержать первый ответ, отправить второй | Нет дубля submit; первый запрос отменён/игнорируется; поздний ответ не затирает новый. |
| FE-009 | Цена/часы | Карточка с ценой на границе бюджета, `max_hours=null` и с числом | Цена всегда «от»; `null` — «не применимо», а не 0/«без лимита». |
| FE-010 | Флаги | Подать все комбинации `synthetic/city_imputed/price_imputed` | Каждый true-флаг виден; false не создаёт ложную метку; флаги не похожи на rating. |
| FE-011 | Объяснения | Три карточки с разным `explanation` | Тексты не обрезаны, визуально различимы; frontend не дописал «отличный выбор». |
| FE-012 | Безопасный текст | Передать HTML/инструкции в `explanation`, `message`, `conditions_to_confirm` | Текст экранирован; скрипт/обработчик не исполнен; `dangerouslySetInnerHTML` нет. |
| FE-013 | Порядок | Подать три ID в заданном порядке, повторить | DOM-порядок совпадает с API; key равен `id`; frontend не сортирует. |
| FE-014 | Invalid response | Нарушить схему и инварианты счётчиков | Целый ответ отклонён; service error; нет частичных карточек. |

## 3. Contract и интеграция с Go backend

Эти проверки запускаются только против реального endpoint. Пока endpoint нет, их статус — **blocked by backend**, а не passed.

| ID | Требование | Запрос/сбой | Ожидание |
|---|---|---|---|
| INT-001 | Фактическая схема | Contract tests для success, 422, 503 | Все DTO проходят runtime-схему; CORS и content type корректны. |
| INT-002 | Влияние даты | Алматы, Ведущий, корпоратив, 1 000 000 KZT, русский, 6 ч; даты 2026-11-14 и 2026-12-19 | Первая дата: 4 допустимых, top-3 `HK-44923`, `HK-29829`, `HK-27222`; вторая: один `HK-35215`. Frontend показывает разную выдачу. |
| INT-003 | Нет категории | Астана + Декоратор, остальные поля валидны | `NO_CATALOG`, не ошибка и не `NO_MATCH`. |
| INT-004 | Категория есть, все исключены | Запрос INT-002 с бюджетом 100 000 KZT | `NO_MATCH`; видна причина бюджета. |
| INT-005 | Занятость и площадки | Сценарии backend-тестов для людей и банкетного зала | Занятый ID не приходит; UI не делает исключение сам. |
| INT-006 | Границы | Цена ровно бюджету; часы ровно `max_hours`; язык задан/опущен | Backend включает границы, опциональные фильтры применяет только при наличии; UI не искажает. |
| INT-007 | `max_hours=null` | Алматы, Флорист, свадьба, 2026-11-14, 300 000 KZT, русский, 6 ч | Допустим `HK-90001`; UI показывает synthetic и не превращает `null` в 0. |
| INT-008 | Детерминизм | Повторить INT-002; backend перемешивает CSV без изменения данных | Одинаковые ID/порядок; frontend сохраняет его. |
| INT-009 | Каталог неготов | Нет файла, некорректный CSV, дубль `id` | Go API даёт `503 CATALOG_UNAVAILABLE`; frontend показывает service error, не пустую выдачу. |
| INT-010 | Некорректный ввод | Подменить дату/числа, обойдя client validation | Go API даёт 422; frontend маппит детали на поля. |
| INT-011 | Объяснения/AI | Недоступен AI; в `description` есть инструкция | Backend даёт фактическое fallback-объяснение; состав/порядок сохранён; frontend текст только экранирует. |

## 4. P1-проверки альтернатив

Выполняются только после появления backend-контракта Alternative:

- каждая альтернатива меняет ровно дату или бюджет;
- повторный backend-поиск даёт не меньше одного кандидата при всех других прежних условиях;
- UI показывает старое и новое значение, не меняет форму без клика;
- после клика уходит обычный SearchRequest, а не скрыто ослабленный запрос;
- frontend не обещает глобально минимальное изменение.

## 6. Критерий готовности frontend

Frontend P0 готов, когда FE-001…FE-014 проходят, DEMO-001…DEMO-008 пройдены вручную, а clean install/build/test воспроизводимы. Готовность frontend на mock **не означает** готовность интеграции. Сквозная готовность требует INT-001…INT-011 на фактическом Go API.
