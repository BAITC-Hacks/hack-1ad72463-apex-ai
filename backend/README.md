# HackAlem backend

Сервис подбора event-подрядчиков на Go 1.25 и PostgreSQL 16. Принимает параметры мероприятия, возвращает до трёх подходящих профилей с конкретными объяснениями и причинами сокращения выдачи. Данные: 66 исходных профилей, 17 категорий, календарь с **2026-09-23 по 2026-12-31 включительно**.

Реализация следует бизнес-правилам [TECH_SPEC.md](https://github.com/BAITC-Hacks/hack-1ad72463-apex-ai/blob/main/TECH_SPEC.md) и HTTP-контракту [ARCHITECTURE.md](https://github.com/BAITC-Hacks/hack-1ad72463-apex-ai/blob/main/ARCHITECTURE.md). Стек изменён на Go/PostgreSQL по запросу заказчика. Весь код, данные, конфигурация, документация и тесты находятся в `backend`.

**Все эндпоинты, поля и примеры ошибок:** [ENDPOINT.MD](ENDPOINT.MD). **Проверки и результаты:** [TESTING.md](TESTING.md).

## Запуск через Docker Compose

Все команды ниже выполняются из папки `backend`. Нужны Docker Engine и Compose v2.

```sh
docker compose up --build -d
curl --fail http://localhost:8080/readyz
sh scripts/smoke.sh
```

Compose поднимает PostgreSQL, применяет миграции и загружает CSV через одноразовый сервис `init`, затем запускает API. Данные PostgreSQL сохраняются в `.tmp/postgres-compose`. Доступны API на `127.0.0.1:8080` и БД на `127.0.0.1:54329`. Указанный в Compose пароль предназначен для локального демо. Для внешнего развёртывания задайте собственный `DATABASE_URL` и учётные данные.

```sh
docker compose logs api
docker compose down
```

`down` останавливает сервисы и сохраняет каталог. При изменении CSV/фактов пересоберите образ и явно повторите импорт:

```sh
docker compose build
docker compose run --rm init
docker compose up -d api
```

## Локальный запуск Go

Нужны Go 1.25+ и PostgreSQL 16+. Можно поднять только БД из Compose или указать существующую **выделенную для этого сервиса** базу.

```sh
docker compose up -d db
cp .env.example .env
# При необходимости измените DATABASE_URL в .env.
set -a
. ./.env
set +a
make deps
make bootstrap
make run
```

Приложение самостоятельно не читает `.env`: загрузите переменные командой выше. `make bootstrap` сначала проверяет файлы, затем применяет миграции и атомарно заменяет каталог. Для раздельного управления есть `make migrate`, `make import`, `make catalog-check`. Последняя команда проверяет файлы без доступа к БД.

Бинарные файлы собираются через `make build`: `bin/server`, `bin/catalog`. Команды CLI: `catalog check|migrate|import|bootstrap`. HTTP-сервер намеренно не меняет схему или данные при старте. Если база недоступна, не инициализирована или каталог повреждён, `/healthz` работает, `/readyz` и каталоговые API возвращают `503`.

## Конфигурация

| Переменная | Значение по умолчанию / назначение |
|---|---|
| `DATABASE_URL` | Обязательна для сервера, миграций и импорта; PostgreSQL DSN |
| `HTTP_ADDR` | `:8080` |
| `CORS_ORIGINS` | Пусто; список точных origin через запятую. В Compose разрешены `http://localhost:3000,http://localhost:5173` |
| `CATALOG_CSV` | `data/catalog.csv`; используется CLI |
| `CATALOG_META` | `data/catalog.meta.json`; явное окно календаря |
| `CATALOG_FACTS` | `data/facts.json`; `-` отключает факты и включает объяснения только по структурированным полям |
| `TEST_DATABASE_URL` | Только тесты; база с правом создания отдельной схемы |

В образе Docker используется порт 8080, его healthcheck обращается к `/readyz` на этом порту. Для PostgreSQL вне локального демо настройте TLS параметрами DSN. API не требует ключей LLM или подключения к внешним сервисам.

## Устройство

```text
cmd/server/                  HTTP-сервер и корректная остановка по SIGTERM
cmd/catalog/                 проверка, миграции и импорт
internal/domain/             модели, нормализация, версии
internal/catalog/            строгий CSV-загрузчик и проверка доказательств
internal/matching/           ограничения, воронка, сортировка, объяснения
internal/postgres/           pgx, транзакции и контроль целостности снимка
internal/postgres/migrations/ встроенные версионированные SQL-миграции
internal/httpapi/            HTTP-контракт, CORS, ошибки, логи и метрики
internal/config/             переменные окружения
data/                        оригинальный CSV, окно календаря, проверенные факты
scripts/smoke.sh              демонстрационные HTTP-запросы
```

`net/http` обслуживает запросы, `pgx/v5` работает с PostgreSQL, `golang.org/x/text` обеспечивает Unicode NFC и case folding. Зависимости зафиксированы в `go.mod`/`go.sum`. Команды Make хранят кеши Go и временные файлы внутри этой папки.

Импорт проверяет **весь** CSV до записи. PostgreSQL хранит профили типизированными колонками: массивы категорий/языков/форматов, `date[]` календаря, nullable `max_hours`, цена `bigint`, булевы флаги. Метаданные и проверенные факты хранятся в `catalog_state`. Импорт сериализуется advisory lock и выполняется одной транзакцией. Неудачный импорт оставляет прежний снимок нетронутым.

Каждый запрос читает 66 профилей и метаданные одной транзакцией `REPEATABLE READ`, проверяет количество, хеш содержимого и ограничения. Это обеспечивает согласованность во время повторного импорта и обнаруживает частичную загрузку/ручное изменение данных. Чтение маленького каталога целиком позволяет сохранить полную воронку причин. Прямое редактирование таблиц не поддерживается: обновляйте исходные файлы и импортируйте заново.

В отличие от исходной предложенной архитектуры, источником для HTTP служит PostgreSQL. Постоянного кеша каталога и объяснений нет: локальная сборка шаблонов дешева, а чтение БД на запрос позволяет немедленно видеть новую версию и сбои. Добавлять Redis, векторную БД или LLM для запуска не требуется.

## Правила подбора

1. Строгая проверка JSON, обязательных полей, типов и календарного окна. Неизвестные поля отклоняются.
2. Точное совпадение нормализованного города и одной категории: NFC, схлопывание пробелов, Unicode case folding. Без нечёткого поиска и скрытой замены запроса.
3. Формат → бюджет → язык → длительность → занятость. Все нарушения вычисляются, но в публичной воронке профиль считается только на первом проваленном шаге.
4. Подходящие профили сортируются по `price_from_kzt ASC`, затем `id ASC`, возвращаются первые три.
5. Для каждой карточки строятся два предложения: проверенные условия запроса и конкретная особенность профиля. При отсутствии фактов остаётся шаблон по структурированным полям.

Цена «от» относится к мероприятию, не умножается на часы и не гарантирует итоговую стоимость. Цена, равная бюджету, и часы, равные лимиту, допустимы. `max_hours = null` означает неприменимость ограничения. Отсутствующие/`null` язык и длительность пропускают соответствующие проверки. Флаги `synthetic`, `price_imputed`, `city_imputed` возвращаются явно и не влияют на порядок.

Одна категория в запросе означает бюджет на одного подрядчика, а не на всё мероприятие. Календарь содержит локальные даты без времени и смещения UTC. Фраза «не отмечено занятым» относится только к календарю датасета. Бронирование, платежи, авторизация, уведомления и актуализация календарей в MVP не входят.

## Происхождение данных и объяснений

`data/catalog.csv` — неизменённая копия приложенного `hackathon dataset anonymized .csv`: 66 строк, 13 полей, 13 синтетических профилей уже были в источнике. HTML-превью имеет сокращённые описания и не используется для загрузки. DOCX с задачей №79-lite использован для проверки требований.

`data/facts.json` содержит 66 особенностей и 2 условия для уточнения. Они отобраны и сопоставлены с текстом исходных описаний при реализации. Каждая запись содержит ID подрядчика, ID факта, точную цитату, хеш полного описания, тип и `review_status: approved`. Статус означает проверку соответствия тексту, **не независимую проверку рекламного заявления или ручное одобрение владельцем сервиса**. При изменении описания старый факт не проходит импорт. Само совпадение цитаты и хеша не доказывает смысл пересказа: новые формулировки надо отдельно проверять; текущие особенности используют прямые выдержки.

Условия аренды фотобудки от трёх часов и тиража сувениров от 20 штук показываются в `conditions_to_confirm`. Они не становятся скрытыми обязательными фильтрами. Сведения о вместимости, оснащении и составе группы в описании не означают, что всё перечисленное включено в стартовую цену.

Онлайн-LLM адаптера нет: выбран предусмотренный архитектурой шаблонный MVP с заранее подготовленными фактами. Поэтому отключение сети или отсутствие API-ключа не меняет выдачу. Тексты описаний не исполняются и не используются как инструкции. При запуске с `CATALOG_FACTS=-` следует заново импортировать каталог, чтобы переключить его на объяснения только по структурированным полям.

## Наблюдаемость

Логи JSON содержат `request_id`, HTTP-статус, время, версии каталога, бизнес-исход, воронку, выбранные ID и `explanation_source: template`. Полные описания и DSN в HTTP-логах не сохраняются. Ответы содержат `X-Request-ID`; ошибки БД не раскрывают служебные пути клиенту.

`/metrics` возвращает счётчики HTTP-статусов и p50/p95 последних 1024 завершённых запросов в текстовом формате Prometheus. Это локальные скользящие наблюдения процесса, сбрасываемые при рестарте, а не агрегированный SLA. Readiness требует доступного целого каталога; liveness от БД не зависит. Лимит JSON — 64 KiB, срок чтения БД на запрос — 5 секунд, настроены HTTP-таймауты и корректная остановка сервера.

## Тесты

```sh
make test                  # unit/HTTP; интеграционные тесты выполняются, если задан TEST_DATABASE_URL
make test-integration      # требует TEST_DATABASE_URL, проверяет работу с настоящим PostgreSQL
make check                 # gofmt и go vet
make build
make benchmark
```

Интеграционный тест использует собственную уникальную схему и удаляет только её. Он проверяет миграции, повторный импорт, откат при ошибке внутри транзакции, согласованность параллельных чтений/импортов, повреждение каталога и отказ БД. Внешний PostgreSQL тест сам не запускает. Без `TEST_DATABASE_URL` он отмечается как `SKIP`, а не как выполненная проверка БД.
